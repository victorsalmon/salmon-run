# Skill: Handoff

**Purpose**: Compact the current session into a handoff document for another agent, or store a raw idea as a Plan Stub for the Planner to develop later. Three variants: Plan Stub, Cowork Stub, Final Handoff.

**Owner**: Any agent. Cowork agents invoke this at session end per the Cowork Workflow.

**Output location**: `Tasks/Handoff/<date>-<topic>.md`

**Trigger**: Session context growing large, user says "handoff" / "final handoff" / "save this for later", or Cowork session ends.

---

## Variants

### Fork-Stub (`type: fork-stub`)

A **prospective** context-transfer document. Captures ALL context needed for a goal being offloaded to a parallel `opencode --continue --fork` session. Unlike a Cowork Stub (retrospective — what happened), a Fork-Stub is forward-looking — files, decisions, state, references, even shared context that overlaps with the original session.

Generated by `Skills/Workflows/Cowork/Scripts/New-ForkStub.ps1` during a `/fork` command.

```
# Fork-Stub: <topic>

**Goal**: <what the forked session should achieve>

## Transferred Context

<all context: files, decisions, state, unresolved questions, references,
including any shared context that overlaps with the original session>
```

### Plan Stub (`type: plan-stub`)

A raw idea too early for a full session plan. Captures direction without polluting an active agent's context. The Planner will find and develop these.

```
# Plan Stub: <topic>

**Type**: plan-stub
**Date**: <date>
**Source**: <what triggered this — browsing, conversation, insight>

## Idea

<2-4 sentences describing the direction>

## Key references

- <file paths or URLs>

## Suggested when ready

<what would trigger turning this into a session plan>
```

### Final Handoff (`type: final-handoff`)

Written when context is near capacity or user says "final handoff". **Final for the agent, not final for the task.** Maximum-context dump.

**Prerequisite — supersede prior handoffs**: Before writing, scan `Tasks/Handoff/*.md` for existing handoff files (any variant: `cowork-stub`, `fork-stub`, or `final-handoff`) that relate to the same topic. For each matching file:

1. **Read** the file to extract its to-do items — `## Incomplete Items` table rows (in final-handoff), `## What Next Agent Needs` numbered list (in cowork-stub), or `**Goal**` (in fork-stub).
2. **Transfer** those to-do items into the new Final Handoff's `## Incomplete Items` section (prefix each with `[from: <superseded-filename>] — `).
<!-- doc-lint: exempt -->
3. **Move** the superseded handoff from `Tasks/Handoff/` to `Tasks/Complete/` under a sub-folder named after the new handoff's topic (e.g., `Tasks/Complete/2026-06-15-fleet-creds/2026.05.30-credential-handoff.md`).

This ensures `Tasks/Handoff/` stays clean — only the latest handoff for any topic lives there, and no to-do items are lost across handoff generations.

**Prerequisite ≡ existing docs**: If the topic already has documentation in the repo's `docs/` directory, update it first. The handoff doc then references the documentation rather than duplicating its content.

```
# Final Handoff: <topic>

**Type**: final-handoff
**Date**: <date>
**Reason**: <context capacity | milestone complete | user request>
```

## Lifecycle: When Handoff Docs are Finished

Handoff docs (Plan Stubs, Cowork Stubs, Final Handoffs) live in `Tasks/Handoff/` while the work is active. **Multi-session cowork plans** often span several sessions, which is why they live in `Tasks/Handoff/` rather than only in agent memory — subsequent sessions can pick up the plan state and resume.

<!-- doc-lint: exempt -->
When the work tracked by a handoff doc is **fully finished** (every remaining task done, verified, and the user has confirmed closure), move the file from `Tasks/Handoff/` into `Tasks/Complete/` under a sub-folder named after the plan (e.g. `Tasks/Complete/2026-06-15-cowork-bookkeeping-phase3/2026.05.30-bookkeeping-phase3.md`). This keeps `Tasks/Handoff/` clean for in-flight plans.

Single-session handoffs and final handoffs that have already been reviewed and closed should move to `Tasks/Complete/` on closeout. Cowork Stubs that were superseded by a Final Handoff should be moved together with the Final Handoff.

**Superseding rule**: When a Final Handoff is written, it **must** scan `Tasks/Handoff/` for handoffs on the same topic, transfer their to-dos into the new document, and move the superseded files to `Tasks/Complete/`. See the Final Handoff prerequisites above for the exact procedure. This applies whether the Final Handoff is written manually or via `New-FinalHandoff.ps1`.

## Handoff Pickup Verification Protocol

**Problem**: Handoffs are written at session end and read at session start. Between those two events, the live system may have changed — containers restarted, transactions processed, files moved, secrets rotated. Treating a handoff as ground truth propagates stale context into the new session.

**Rule**: A handoff is a **hypothesis, not a contract**. Every claim in it must be independently verified before the agent proceeds with work. The pickup agent **rewrites** the handoff with verified values before starting Phase 1.

### Verification Categories

| Category | Examples | Verification Method |
|----------|----------|-------------------|
| **State counts** | "42 receipts unmatched", "3 vendors pending" | Query the live system: API call, CLI command, `Invoke-StatusCheck`, or direct file read |
| **File existence** | "Config at `foo/bar.json`" | `Test-Path`, `Get-ChildItem`, `git log` |
| **File content** | "`script.ps1` was modified to add X" | `git diff HEAD~1`, or read the file and confirm the described change is present |
| **Blockers** | "Blocked on AWS SSO — token expired" | **Test the blocker**: run the command that failed. If it now succeeds, the blocker is resolved — remove it from Incomplete Items |
| **Verification claims** | "Test XYZ passed" | Re-run the verification: `Invoke-Expression $evidence` or the test command. If it fails, the item is NOT verified |
| **Tool/skill claims** | "Use skill S for task T" | Check the skill file exists at the claimed path and its description matches the claimed purpose |
| **Live container/API state** | "Container X is healthy on port Y" | `docker ps`, `curl /api/health`, or MCP tool probe |
| **External credential state** | "Zoho OAuth token is valid" | Make a lightweight API call (`GET /zoho/books/organizations` or equivalent). If 401, flag for re-auth |

### Verification Procedure (Mandatory — All Handoff Pickups)

When an agent picks up a handoff document from `Tasks/Handoff/`, it **must** follow this procedure before proceeding to Phase 1:

1. **Read the handoff** — Understand every section, table, and claim it contains.

2. **Build a verification table** — Extract every verifiable claim into a structured table with columns:
   - `#` (claim number)
   - `Claim` (verbatim excerpt)
   - `Source` (section/field in handoff)
   - `Verification Method` (exact command, API call, or check)
   - `Actual Value` (what the live system reports)
   - `Match?` (Yes/No/Partial)
   - `Action` (what to do if mismatch)

3. **Execute verifications** — Run each verification method and record the actual value. Batch sibling checks (e.g., all file-existence checks) for efficiency.

4. **Classify each claim**:
   - **Verified** (✅): Actual value matches the claim exactly. No action needed.
   - **Stale** (⚠️): Actual value differs. The handoff claim is outdated.
   - **Unverifiable** (❓): No live check available. Mark explicitly and explain why.
   - **Erroneous** (❌): Claim is provably wrong. Must be corrected.

5. **Rewrite the handoff** — Create an updated version with:
   - All stale counts replaced with current values
   - Resolved blockers removed from Incomplete Items
   - New blockers (discovered during verification) added
   - File paths corrected if they moved
   - Verification results appended: a summary table showing what was verified and what changed

   The rewritten handoff replaces the original in `Tasks/Handoff/`. The original moves to `Tasks/Complete/` under a sub-folder named after the new handoff topic.

6. **Block until verified** — If a claim is **critical to the session** (e.g., "the Bookkeeping container is healthy on port X") and **verification fails** (container is down, API returns 500), the agent must:
   - Fix the issue if possible (e.g., restart the container)
   - OR mark the session as blocked and write a manual task
   - OR skip the handoff entirely and start fresh

   Do NOT proceed with a session built on a failed critical verification.

7. **Proactive Discovery** — After verifying all explicit claims, run discovery sweeps to find context the handoff author may have missed:
   a. **Run grep patterns**: For each pattern in ## Quick Reference > Grep Patterns, execute it and confirm the results are consistent with the handoff's claims. If a pattern returns 0 results, the code has been refactored — flag the entry as stale in the rewrite.
   b. **Directory sweep**: For each directory in ## Key Directories, check if files were added or modified since the handoff's `Date` field. Log newly relevant files for the rewrite.
   c. **Git log sweep**: For each file in ## Key Files, run `git log --oneline -5 <file>` to detect post-handoff changes by other agents.
   d. **Topic dependency discovery**: Run a codebase-wide grep for the handoff's core topic terms (function names, module names, config keys) to surface files the handoff author did not list. Add relevant findings to the rewritten handoff.
   e. **Categorize findings**: Each discovery is either a **correction** (stale claim, missing file, erroneous link) or an **enrichment** (new file, new pattern, new link). Corrections update existing claims; enrichments create new rows in ## Quick Reference or ## Key Files.
   f. **Link verification**: For each URL in ## Quick Reference > External Links, attempt to reach the resource (HTTP HEAD or equivalent). Flag dead links.

### Per-Variant Verification Checklists

#### Cowork Stub

| Section | What to Verify | How |
|---------|---------------|-----|
| `## Current State` | Every state count, status, or phase assertion | Query live system or read authoritative file |
| `## Memory Reference` | The memory file exists and its `Last verified` timestamp is fresh | `Test-Path`, read the file |
| `## What Worked / ## What Didn't Work` | Any referenced file paths exist, code behavior claims | `Test-Path`, `git log`, `Test-*` |
| `## Skills Used` | Each skill exists at the claimed path | `Test-Path` |
| `## What Next Agent Needs` | Every file, API, or system referenced is accessible | Attempt to access each one |
| `## Key Files` | Every file path exists | `Test-Path` or `git ls-files` |
| `## Quick Reference` | Grep patterns return results, directories exist, URLs reachable | Execute pattern, `Test-Path`, HTTP HEAD |

#### Final Handoff

| Section | What to Verify | How |
|---------|---------------|-----|
| `## Completed Items` | Every `Evidence` cell — re-run the verification command | `Invoke-Expression` the described test/command |
| `## Incomplete Items` | Every `Current State` and `Blocker` — is it still accurate? | Re-check each: query live system, re-test each blocker |
| `## Tools & Approaches — What Worked` | Tool still available, paths still valid | `Get-Command`, `Test-Path` |
| `## Tools & Approaches — What Didn't Work` | Still true? (may have been fixed by another agent) | Re-test the failed approach |
| `## Suggested Skills` | Skill exists at claimed path | `Test-Path` |
| `## Key Files` | Every file path exists | `Test-Path` or `git ls-files` |
| `## Redirects / Deprecations` | Old paths still redirected? New paths valid? | Test both old and new paths |
| `## Quick Reference` | Grep patterns return results, directories exist, URLs reachable | Execute pattern, `Test-Path`, HTTP HEAD |

### Verification Block (Handoff Appendix)

Every handoff that has been verified must carry a `## Verification` appendix:

```markdown
## Verification

Verified by: <agent-id>
Verified at: <ISO-8601>
Verification count: N/M claims matched
Stale claims corrected: <count>

| # | Claim | Source | Method | Actual | Match |
|---|-------|--------|--------|--------|-------|
| 1 | ... | ... | ... | ... | ✅/⚠️/❌ |

Stale corrections:
- Claim 2: count was 42, corrected to 37
- Claim 5: "blocked on X" → unblocked, removed from Incomplete Items
```

### Skip Conditions

Verification may be skipped ONLY when:
1. The handoff was written and picked up in the **same continuous session** (same agent ID, no intervening work by other agents)
2. The handoff carries a `## Verification` appendix from a previous pickup that is **less than 1 hour old**
3. The topic is a **Plan Stub** (speculative, no state claims to verify)

In all other cases, verification is **mandatory**. A session that starts without verifying its handoff is in violation of protocol.

## General Rules (All Variants)

1. **Do not duplicate** content already captured in existing documentation (`docs/`), ADRs, session plans, or commits. Reference them by path instead.
2. **Redact** sensitive information (API keys, passwords, PII).
3. **Test-Before-Report**: Every completed item in a Final Handoff must include how it was verified (test pass, API response, command output, screenshot). Narrative-only claims are unreliable — agents can experience Taskbleed.
4. **Documentation in `docs/`**: Per ADR 0030, documentation is organized by topic in `docs/` with no rigid naming convention. Agents should reference documentation paths directly when writing handoff docs.
5. **Orphan references**: List only orphan files in ## Key Files. Non-orphan references should use grep patterns or directory hints in ## Quick Reference instead — a single pattern is more compact and more robust than a static file list.
6. **Redirects**: If files moved during the session, list old→new paths so the next agent doesn't chase stale locations.
7. **Documentation first**: For Final Handoffs, always write/update the relevant documentation in the repo's `docs/` before writing the handoff doc. The handoff doc refers to the documentation; it does not replace it.
8. **Verification appendix**: Every handoff that has been processed through the Pickup Verification Protocol must carry a `## Verification` appendix (see above). This prevents the next agent from re-verifying already-verified claims.
