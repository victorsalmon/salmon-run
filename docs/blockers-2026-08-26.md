## 1. Live provider execution

### Blocker
The provider executors for OpenCode, OpenCode Go, DSH, OpenRouter,
DeepInfra/Codex, and Devin build real CLI commands, but none of them have
been exercised against a live provider endpoint.

### Why not actioned
- Requires real provider credentials that are not committed to the public repo.
- The installed `opencode` CLI (1.18.21) has a different argument shape than the
  current `Opencode.ps1` executor (`--command work-{role}-once --effort`
  vs. `run <prompt> --model --variant --auto -f`). Aligning it is a separate
  implementation task, not release hardening.
- Other provider CLIs (`openrouter`, `dsh`, `codex`, `devin run`) are not
  installed in this environment.

### Path to resolution
1. Choose one provider that already has a CLI and a usable free/cheap tier
   (recommended: `opencode` with `opencode/hy3-free`).
2. Update its Salmon Run executor to match the actual CLI arguments.
3. Run a single plan end-to-end with `Start-SalmonRun.ps1 -Run`.
4. Verify the plan lands in `Tasks/Complete` and that `PondLog` cost/benchmark
   fields are populated.
5. Repeat for paid providers once keys are available.

### Still needed
- Provider API key(s) or confirmed free-tier access.
- Decision on whether `--auto` is acceptable for headless `opencode` runs.

## 2. Full `Start-SalmonRun.ps1 -Run` lifecycle

### Blocker
`Start-SalmonRun.ps1 -DryRun` is tested, but `-Run` has not been exercised
through the full pond lifecycle (Code → Review → Audit → QA → Complete →
Archive) with a real executor.

### Why not actioned
- `-Run` depends on live provider execution (blocker 1); the local executor is
  the only one that is fully green, and it already has Pester coverage.
- End-to-end lifecycle testing is blocked until at least one non-local provider
  is proven.

### Path to resolution
After the `opencode` executor is aligned, drop a plan with a `Daily` or `Flash`
tier into `~/.salmon/Tasks/Code` and run `Start-SalmonRun.ps1 -Run -MaxIterations
<N>`. Confirm the plan progresses through every pond and is archived.

### Still needed
- A working real provider (see blocker 1).

## 3. Pre-existing `SalmonRun.Constants` and `SalmonRun.Process` Pester failures

### Path to resolution

4C bug-fix workflow (`4c-concern` → `4c-cause` → `4c-countermeasure` →
`4c-check`).

### Still needed

## 5. Cross-platform support guarantees

### Blocker
The package has been validated on Windows. macOS and Linux behavior is
inferred from the PowerShell/Docker packaging but not proven.

### Why not actioned
- The current environment is Windows; no macOS or Linux runner is available.
- `install.ps1` updates the user `PSModulePath` via `Environment::SetEnvironmentVariable`,
  which is Windows-centric and may need profile logic on non-Windows.

### Path to resolution
- Run `install.ps1` and the focused Pester suite in a clean macOS and Linux
  environment (GitHub Actions `macos-latest` and `ubuntu-latest` would work).
- Add any platform-specific `PSModulePath`/profile handling needed.

### Still needed
- CI runner time or a local non-Windows environment.

## 6. Canonical source governance

### Blocker
The README states that `salmon-orchestrator` is the canonical source and
`salmon-run` is the public projection, but the public repo has 40+ commits and
may have diverged. It is not clear which repo is the active source of truth.

### Why not actioned
- This is a repository/process decision, not a code change.
- `Sync-FromCanonical.ps1` exists and is parameterized, so the technical path
  is already in place.

### Path to resolution
Decide and document:
- Will `salmon-orchestrator` remain canonical and `salmon-run` be rebuilt from
  it for each release?
- Or will `salmon-run` become the source of truth and `salmon-orchestrator`
  be archived?

### Still needed
- Decision from the project owner.

## 7. Runtime state in the source working tree

### Blocker
A large `Tasks/` tree exists under the repository root (`<repo-root>\Tasks`).
It is `.gitignore`d and not committed, but it shows the orchestrator is using
its source tree as a runtime home instead of `~/.salmon`.

### Why not actioned
- This is an operational hygiene issue, not a public-package defect.
- `install.ps1` and the Docker image already default to `~/.salmon` or
  `/salmon-home`.

### Path to resolution
1. Set `SALMON_RUN_HOME` to a directory outside the repo.
2. Delete or archive the repo-root `Tasks/` tree.
3. Add a note to `README.md` or `PUBLIC_PACKAGE.md` about runtime-home hygiene.

### Still needed
- A clean-up window where the orchestrator is not actively running.
